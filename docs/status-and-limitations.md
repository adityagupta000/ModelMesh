# Status and limitations

Where the project stands: what was verified, what is known to be wrong or missing, what the design deliberately leaves out, and how it got here. Items marked **verified** were reproduced during this review on a real Postgres and Redis. Items marked **reported** come from the project's own completion reports and were not re-run.

## Verdict

**A well-documented development implementation, not production-ready.** The project says so itself, and the evidence agrees.

What is solid: the core request path works and is tested (102 tests pass, reproduced twice); the queue has real retry, dead-letter and crash-recovery behaviour with tests behind it; the registry, canary routing and rollback guard behave as described; the documents the project shipped were largely honest about gaps.

What stands between it and production:

1. **No transport or network security.** No TLS anywhere, no authentication on workers or Redis, open registration, development secrets in the repository. See [Security](security.md).
2. **Fragile capacity behaviour.** A full Redis returns bare HTTP 500s while readiness stays green, and uploads linger in Redis for an hour.
3. **Thin observability.** Metrics need a hand-applied ClickHouse DDL and exist only on Kubernetes; there is no Prometheus, Grafana, alerting or tracing.
4. **Narrow test coverage of the edges.** No end-to-end test, almost no WebSocket coverage, no `PredictStream` test, nothing that exercises the images, manifests or ClickHouse.
5. **Evidence is small-sample.** Latency and memory figures come from a handful of requests with tiny fixtures, run by the author.

## Limits by design

Things the project chose not to build, stated by its own documents and confirmed in the code:

- Prometheus, Grafana and a `/metrics` endpoint; ClickHouse in Compose.
- Ingress, TLS, HPA, PodDisruptionBudgets, NetworkPolicies, Helm, a CI/CD pipeline.
- Multi-tenancy, per-model quotas, batching, GPU support, token-level streaming, a result cache, a Postgres request log, a sliding-window rate limiter.
- Canary on the WebSocket path, automatic promotion, statistical testing, notifications.
- Durable Redis on Kubernetes.
- A job replay tool for the dead-letter stream.
- More than two example models.

## How it got here

The project was built in five feature phases and then hardened in six more, driven by written prompts and reviewed in writing.

| Phase            | Theme                                                               | Outcome (reported)                                                                                                                                                                                                             | Suite                   |
| ---------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------- |
| 1 to 5           | Gateway, async queue, WebSocket and gRPC, Kubernetes, observability | Built. Phase 5 is partial (about 9 of 12 scoped outcomes): no Prometheus or Grafana                                                                                                                                            | n/a                     |
| 0                | Run and baseline                                                    | First Compose build took about 51 minutes; an invalid upload took 92 s to fail; 20 of 21 tests failed                                                                                                                          | 1 pass                  |
| 6                | Reproducible baseline                                               | Schema, ConfigMap and migration made consistent; dead code removed; smoke test added                                                                                                                                           | n/a                     |
| 7                | Trustworthy tests                                                   | Tests run against the app's own database and Redis                                                                                                                                                                             | 20 + 1 expected failure |
| 8                | Gateway correctness                                                 | Input validation, revoked keys rejected on WebSocket, numeric canary, atomic rate limit, real `/ready`                                                                                                                         | 43                      |
| 9                | Queue and worker reliability                                        | Payload in its own key, retry with backoff, DLQ, crash recovery, supervised containers, probes                                                                                                                                 | 54                      |
| 10               | Metrics pipeline                                                    | One row per finished job, ASR metrics, bounded timeouts                                                                                                                                                                        | 64                      |
| 11               | Canary rollback guard                                               | Dry-run CLI that can only reset `canary_percent` to 0                                                                                                                                                                          | 75                      |
| Review follow-up | Fixes from a written code review                                    | Timeouts and disable-when-unset, invalid-audio mapping, WebSocket client exit codes, time-based maintenance, WebSocket size check, key limit bounds, hidden routing, generic `/ready` errors, OCR memory limit raised to 3 GiB | **102**                 |

Decisions recorded along the way: documented-but-missing features are corrected in the documents, not built; new versions must match `v<number>`; no canary on the WebSocket path; Kafka stays and is labelled dormant; the guard only ever sets `canary_percent` to 0; the optional guard CronJob was skipped.

The review's findings R1 to R9 were implemented. The ones that can be confirmed from code were: ClickHouse timeouts and disable-when-unset (R1), ASR invalid-audio handling (R2), WebSocket client exit status (R3), time-based maintenance (R4), WebSocket size check on the default path (R5), key rate-limit bounds (R7), hidden internals and generic `/ready` errors (R8), aligned test dependencies (R10), and the OCR memory limit (R12). R6, the guard's warm-up problem, was handled by documentation only and is reproduced above (issue 5).

## Open work

Suggestions only, roughly in order of value for effort. They are not planned work.

1. Return a deliberate error when Redis refuses a write, and make `/ready` aware of memory (issue 1).
2. Stop returning raw exception text on the WebSocket (issue 2).
3. Delete the payload when a job finishes (issue 3), and decide how a job for an absent worker should fail (issue 4).
4. Fix the guard's warm-up and 100% edge cases, then consider scheduling it (issues 5 to 7).
5. Add the missing tests: one end-to-end path, WebSocket success and auth, `PredictStream`, the full-Redis case.
6. Security basics from [Security](security.md): TLS, a real `JWT_SECRET`, registration control, a Redis password, non-root containers.
7. Remove or finish the dead code (issues 16 to 18) and merge the duplicated worker modules.
8. Add CI that runs the suite against Postgres and Redis service containers.
9. Re-measure memory and latency with realistic documents and larger samples.
